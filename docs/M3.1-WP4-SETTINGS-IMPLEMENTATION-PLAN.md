# M3.1 — WP4: Settings Experience — Implementation Plan

**Status:** Proposed (awaiting approval) · **Date:** 2026-07-15 · **Author:** Lead Product Architect
**Precondition:** WP1 (nav/IA), WP2 (organizations backend + demo store), WP3 complete. No code in this document by design.

---

## 1. Current State (verified against repo)

- **Backend is done.** `src/features/organizations/` exposes `getOrganization`, `updateOrganization`, `getOrganizationMembers`, `updateUserRole`, `deactivateUser`, `reactivateUser` via the standard triple-file dispatcher (`actions.ts` → mock/real on `DEMO_MODE`), each guarded by `requireCurrentUser()` + `requirePermission()`, with owner-protection and activity logging. `updateOrganization` already calls `revalidatePath("/settings/organization")`.
- **Shell is done.** `AppShell` (server) filters `NAV_SECTIONS` by permission; the Settings nav item is `status: "live"`, gated on `["settings", "read"]`; `AppHeader` avatar menu links to `/settings/profile`.
- **Gap:** no `src/app/(dashboard)/settings/` directory exists. Both links 404 into the group `not-found.tsx`.
- **Gap:** no self-service profile-update action exists (WP4 profile page is read-only per M3.1 scope, so none is required).
- **UI kit gaps:** `src/components/ui/` lacks `tabs`, `select`, `textarea`, `alert-dialog` (has field, dialog, table, skeleton, sheet, avatar, sonner, etc.). Components are **Base UI** (`render` prop, not Radix `asChild`) on Tailwind v4 — new primitives must follow that convention.
- **No client user context exists** — pages are server components calling `getCurrentUser()`; client components receive user data as props. WP4 keeps this pattern.

## 2. Decisions

### 2.1 Settings Layout
- New nested layout `src/app/(dashboard)/settings/layout.tsx` **inside** the `(dashboard)` group → inherits AppShell, group `error.tsx`/`not-found.tsx` for free.
- Server component: page header ("Settings" title + description), settings sub-navigation, content slot. Content constrained to a comfortable reading width (~`max-w-4xl`) consistent with existing `p-6 gap-6` main area.
- The layout performs a defense-in-depth `settings.read` permission check (`requireCurrentUser` + `hasPermission`); if denied, render the group not-found (nav already hides the entry, this covers deep links).

### 2.2 Settings Navigation
- Two destinations in M3.1: **Organization** (`/settings/organization`) and **Profile** (`/settings/profile`).
- Desktop (≥768px): vertical sub-nav column at the left of the settings content (links styled like sidebar items, active state by `pathname` prefix — same matching rule as `app-sidebar.tsx`). Client component (`settings-nav.tsx`) since it needs `usePathname`.
- Mobile (<768px): sub-nav collapses to a horizontal, scrollable tab strip above the content (no new dependency; plain links styled as tabs — avoids adding a `tabs` primitive solely for nav).
- Nav item visibility: Organization link shown only when user has `organization.read`; Profile always shown. Item config lives in a small `settings/` config array mirroring the `NavItem` shape (title, href, permission) so future sections (Billing, Integrations) slot in.
- `settings/page.tsx` → server `redirect("/settings/organization")`; if the user lacks `organization.read`, redirect to `/settings/profile` instead.

### 2.3 Organization Profile (`/settings/organization`)
- Server page: `await Promise.all([getOrganization(), getOrganizationMembers()])`, pass to client components. Page composed of three sections (stacked cards, anchored headings): **Profile**, **Members**, **Roles** — sections rather than URL tabs keeps M3.1 to one route and avoids the missing `tabs` primitive; revisit if sections grow.
- **Profile form** (client, `organization-profile-form.tsx`): React Hook Form + `zodResolver(updateOrganizationSchema)` (schema already exists — single source of truth; add `react-hook-form` + `@hookform/resolvers` deps). Fields: organizationName, legalName, slug (read-only display in M3.1 — slug changes have routing/RLS implications, defer), logoUrl, website, industry, timezone, currency, country, address, contactEmail, contactPhone, brandPrimaryColor/SecondaryColor (text input + color swatch preview; native color input as enhancement).
  - Submit calls `updateOrganization` server action; pending state on the button (`useTransition`/RHF `isSubmitting`); success → sonner toast "Organization updated"; thrown errors → destructive toast with message; Zod field errors → inline under fields via the existing `field.tsx` primitives.
  - Entire form rendered read-only (inputs disabled, no submit) when the user lacks `organization.update` — visibility ≠ editability.
- **Members table** (client, `members-table.tsx`): columns Avatar+Name, Email, Role (select), Department, Status (badge), Joined, row action.
  - Role change: `select` primitive listing org roles (fetched server-side via a small `getRoles` addition — see §5, or derived from members' joined roles for M3.1 if we avoid a new action; **decision: add `getRoles()` to the organizations feature** — Roles section needs it anyway). On change → confirm dialog ("Change {name}'s role to {role}?") → `updateUserRole` → toast; optimistic UI not needed at this scale, rely on revalidate.
  - Deactivate/Reactivate: row dropdown action → `alert-dialog` confirmation stating consequences → action → toast. Self-row and last-owner rows: action disabled with tooltip (server still enforces; UI mirrors `deactivateUser`/`checkOwnerProtection` rules).
  - Controls hidden/disabled without `roles.update` / `users.update` respectively; table itself requires `users.read` (page already fetches under that gate — if `getOrganizationMembers` throws `PermissionDeniedError`, the page catches and renders the Members section as a permission notice instead of crashing the route).
- **Roles section** (server, `roles-reference.tsx`): read-only reference of the 6 `SYSTEM_ROLES` (name, description, summarized permission map — module chips, with `*` rendered as "Full access"). No editing in M3.1. Data from `getRoles()` (DB/demo rows), falling back to `SYSTEM_ROLES` constants for descriptions.

### 2.4 Members / Roles routing note
Members and Roles ship as sections of `/settings/organization` in M3.1 (matches the approved M3.1 plan §WP4-3). Sub-nav is built so `/settings/members`, `/settings/roles` can be promoted to routes later without IA churn. **No invite flow** — out of scope (no invite backend exists); Members section header shows a disabled "Invite member — coming soon" affordance to set expectations.

### 2.5 User Profile (`/settings/profile`)
- Server page rendering `CurrentUser` data — no new backend. Identity card: avatar (with initials fallback), full name, email, designation, role badge, department, timezone.
- Preferences card: theme selector wired to `next-themes` (`useTheme` — client island; light/dark/system). This is the only mutable thing on the page and is client-local.
- "Edit profile" deferred (no `updateProfile` action exists); show fields as read-only with a muted note that profile editing arrives in a later milestone. This fixes the header-menu 404 (M3.1 acceptance criterion 6).

### 2.6 Loading
- `settings/loading.tsx`: settings-shaped skeleton — sub-nav skeleton column + stacked card skeletons (form rows, table rows) using the existing `skeleton.tsx`, following the `(dashboard)/loading.tsx` idiom. One shared loading file for the tree is sufficient (both pages are card stacks).
- Mutation pending states: submit buttons show pending (disabled + spinner/label change); role select and row actions disabled while their transition is in flight.

### 2.7 Errors
- Render errors: inherit `(dashboard)/error.tsx` (already handles `unstable_retry` + digest). No settings-specific error boundary needed.
- Action errors: server actions **throw** (established convention — plain `Error`, `ZodError`, `PermissionDeniedError`). Client handlers catch and map: `PermissionDeniedError` → "You don't have permission…" toast; validation → inline field errors; known business errors ("Cannot deactivate yourself", "Cannot modify the last active owner", "Organization not found") → verbatim destructive toast; unknown → generic toast. No `{error}` return-shape migration in this WP.
- Deep-link without `settings.read` → not-found (per §2.1), matching how hidden nav items behave elsewhere.

### 2.8 Empty States
- Members table with ≤1 row (solo owner): dashed-border inline empty-state row — "You're the only member. Member provisioning is admin-managed in V1." (follows the existing inline dashed-card idiom; no new component library).
- `getOrganization()` returning `null` (should not happen post-WP2 seed): dashed card "Organization not found" with a retry hint — never a blank page.
- Missing optional org fields render as placeholder text ("Not set") in read-only mode, empty inputs in edit mode.

### 2.9 Responsive
- <768px (`useIsMobile` breakpoint): sub-nav → horizontal tab strip (§2.2); org form → single column (two-column field grid collapses); members table → the M3.1-approved fallback: stacked member cards below `md` (name/role/status + actions in a dropdown) instead of horizontal scroll, since role-select + actions don't scroll well.
- Verified target: all settings pages usable at 375px; AppShell sidebar sheet behavior untouched.
- Color inputs, selects, and dialogs must be touch-target ≥44px on mobile.

### 2.10 Accessibility
- Sub-nav is a `<nav aria-label="Settings">`; active link `aria-current="page"`.
- Sections have heading hierarchy (page `h1` in layout header, `h2` per card) and `id`s for skip/anchor.
- All form inputs labelled via `field.tsx` primitives; errors associated with `aria-describedby`/`aria-invalid` (verify the Field primitive wires this; add if not).
- Confirm dialogs: focus trapped (Base UI dialog handles), destructive action described in dialog body, initial focus on Cancel.
- Toasts (sonner) are supplementary — outcomes also reflected in the UI (revalidated data, inline errors), never toast-only.
- Members table: proper `<th scope>`, row actions reachable by keyboard, select has an accessible label including the member's name ("Role for Jane Doe").
- Color contrast for status badges and brand-color swatches checked in both themes.

## 5. Acceptance Criteria

1. `/settings` no longer 404s: redirects to `/settings/organization` (or `/settings/profile` when `organization.read` is absent).
2. Header avatar menu → `/settings/profile` renders the current user's name, email, designation, role, department; theme selection works and persists (next-themes).
3. `/settings/organization` shows the real org (demo store in demo mode); every field from `updateOrganizationSchema` is editable (slug read-only); save persists, survives reload, toasts success.
4. Invalid input (malformed URL, bad hex color, bad currency/timezone) shows inline field errors and does not submit; server-side Zod rejection also surfaces inline/toast.
5. Members section lists all org users with role, department, status; role change requires confirmation and persists; deactivate/reactivate work with confirmation and status badge updates after revalidation.
6. Self-deactivation and last-owner modification are blocked in the UI (disabled + tooltip) **and** the server error is surfaced gracefully if forced.
7. A user without `settings.read` sees no Settings nav item and gets not-found on deep link; without `organization.update` the org form is read-only; without `roles.update`/`users.update` the member controls are hidden/disabled; without `users.read` the Members section shows a permission notice, not a crash.
8. Roles section lists the six system roles with descriptions and permission summaries, clearly marked read-only/system.
9. All new pages render correct skeletons via `settings/loading.tsx`; mutations show pending states; failures toast with actionable messages.
10. Usable at 375px: sub-nav tab strip, single-column form, member cards; no horizontal page scroll.
11. Keyboard-only pass: sub-nav, form, role select, dialogs, row actions all operable; dialogs trap focus; active nav link exposes `aria-current`.
12. All activity-logged mutations appear in the activity log (org update, role change, deactivate/reactivate) — already handled by actions; verify not regressed.
