## 1. Permission matrix (from `SYSTEM_ROLES`)

Capability → required permission → roles that hold it:

| Capability                  | Guard          | owner | super_admin | creative_director | project_manager | team_member | finance |
| --------------------------- | -------------- | ----- | ----------- | ----------------- | --------------- | ----------- | ------- |
| View members table          | `users.read`   | ✅    | ✅          | ✅ (read)         | ✅ (read)       | ❌          | ❌      |
| Change role                 | `roles.update` | ✅    | ✅          | ❌                | ❌              | ❌          | ❌      |
| Deactivate                  | `users.update` | ✅    | ✅          | ❌                | ❌              | ❌          | ❌      |
| Reactivate                  | `users.update` | ✅    | ✅          | ❌                | ❌              | ❌          | ❌      |
| Load role list (for select) | `roles.read`   | ✅    | ✅          | ✅                | ✅              | ❌          | ❌      |

Rendering rules:

- No `users.read` → page renders a permission notice (Card, not a crash); server action's `PermissionDeniedError` is caught at the page level.
- No `roles.update` and no `users.update` → Actions column hidden entirely; table is read-only.
- Partial permission → only the permitted menu items render.
- Server actions remain the enforcement layer; all client gating is UX-only (defense in depth).

## 2. Business rules (UI mirrors, server enforces)

| Rule                         | Server (existing)                                                                                                      | UI mirror                                                                                                                                      |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Last Owner Protection        | `checkOwnerProtection()` throws `"Cannot modify the last active owner"` on role change away from owner or deactivation | If member is the **only active owner**: disable “Change Role” + “Deactivate” items with tooltip “This is the organization's last active owner” |
| Self Deactivation Protection | `deactivateUser` throws `"Cannot deactivate yourself"`                                                                 | On the current user's own row: disable “Deactivate” with tooltip “You cannot deactivate your own account”                                      |
| Organization Scope           | Every query/mutation filtered by `user.organizationId`; RLS + `app.is_org_member()` in DB                              | None needed — page only ever receives org-scoped data from `getOrganizationMembers()`                                                          |

Client never pre-decides success — even when enabled, server errors surface verbatim as destructive toasts.

## 3. Page design — `/settings/members`

### 3.1 Data flow (matches organization page pattern)

- **Server page** (`page.tsx`): `requireCurrentUser()` → guard `users.read` (render permission notice on failure) → `Promise.all([getOrganizationMembers(), canReadRoles ? getRoles() : []])` → compute props: `canChangeRole = hasPermission(perms,"roles","update")`, `canToggleStatus = hasPermission(perms,"users","update")`, `currentUserId`, `activeOwnerCount` (derived: members where `role.roleKey === "owner"` and `status === "active"`).
- **Client component** (`members-table.tsx`): pure presentation + action dialogs. No react-query; mutations via server actions inside `useTransition`, relying on `revalidatePath` (no optimistic UI). Actions must also `revalidatePath("/settings/members")` (add alongside the existing `/settings/organization` revalidation).

### 3.2 Table (desktop ≥ `md`)

Columns using existing `Table*` primitives:

| Column      | Rendering                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Member      | `Avatar` (`AvatarImage` from `avatarUrl`, `AvatarFallback` = initials from first/last name) + name; “(you)” suffix on own row |
| Email       | plain text, truncate with title attr                                                                                          |
| Role        | `roleName` text; `Badge variant="outline"` if `isSystem`                                                                      |
| Status      | `Badge` — `default` for active, `secondary` for inactive (existing idiom)                                                     |
| Last Active | “—” + tooltip (Ruling 2)                                                                                                      |
| Actions     | `DropdownMenu` (ghost icon button, `aria-label="Actions for {name}"`): Change Role / Deactivate (destructive) or Reactivate   |

Sorted as returned (`createdAt asc`). No pagination in V1 (org sizes are small; note as future work).

### 3.3 Actions

- **Change Role** — `Dialog`: labelled `Select` (“Role for {name}”) populated from `getRoles()`, preselected to current role, description of consequence → Confirm calls `updateUserRole` → success toast “Role updated for {name}”.
- **Deactivate** — `AlertDialog` (new primitive): “Deactivate {name}? They will lose access until reactivated.” Cancel receives initial focus; Confirm is destructive → `deactivateUser` → toast.
- **Reactivate** — `AlertDialog`: symmetric copy → `reactivateUser` → toast. Shown only on inactive rows.

Error mapping in every handler: `PermissionDeniedError` → “You don't have permission to do that”; Zod message or known business errors (“Cannot deactivate yourself”, “Cannot modify the last active owner”) → verbatim `toast.error`; unknown → generic failure toast. Dialog stays open on error.

### 3.4 UI states

- **Loading:** `settings/members/loading.tsx` — table-shaped skeleton (header row + 5 skeleton rows: circle + two bars), using `Skeleton`. (Do not touch the shared settings spinner.)
- **Error:** inherited `(dashboard)` `error.tsx` for render failures; action failures via toasts (§3.3); permission failure via in-page notice card.
- **Empty:** ≤1 member → dashed-border inline state (existing idiom): “You're the only member. Member provisioning is admin-managed in V1.” Plus a disabled “Invite member — coming soon” button in the page header regardless of count (invite backend is explicitly out of scope).
- **Responsive:** below `md`, render stacked member cards (avatar/name/email, role + status badges, same dropdown) instead of a horizontally-scrolling table; usable at 375px.
- **Accessibility:** `<th scope="col">`; every action keyboard-reachable; select labelled with the member's name; dialogs trap focus with initial focus on Cancel; status conveyed by text in badge, not color alone; icon-only trigger has `aria-label`.

## 6. Acceptance criteria

1. `/settings/members` renders for any user with `users.read`; users without it see a permission notice, not an error page or crash.
2. Table shows Avatar, Name, Email, Role, Status badge, Last Active (“—” + tooltip), Actions for every org member; current user's row is marked “(you)”.
3. Change Role: role select lists org roles from `getRoles()`, confirm dialog names the member, success toast fires, table reflects the new role after revalidation without manual refresh.
4. Deactivate/Reactivate: confirmation dialog → status badge flips after revalidation; Reactivate only appears on inactive rows.
5. Last-owner row: Change Role and Deactivate disabled with explanatory tooltip; forcing the server call anyway returns “Cannot modify the last active owner” as a toast.
6. Own row: Deactivate disabled with tooltip; server independently rejects with “Cannot deactivate yourself”.
7. Users lacking `roles.update`/`users.update` see no corresponding menu items; with neither, the Actions column is absent.
8. All data and mutations are org-scoped; no cross-org member ever renders (verify via demo store fixtures).
9. Empty state and disabled “Invite member — coming soon” affordance render per §3.4.
10. Mobile (375px): stacked cards, all actions reachable; no horizontal page scroll.
11. Full behavior parity between real and mock action paths (demo mode).
