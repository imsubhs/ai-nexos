## 1. Architecture implemented

Layered architecture per TRD §4, realized as a single Next.js 16 application
over Supabase:

- **Presentation** — App Router route groups: `(auth)` public auth pages,
  `(internal)` authenticated shell, `portal/` login-free client portal.
- **Edge routing** — `src/proxy.ts` (Next 16 proxy convention): dual-domain
  host routing, Supabase session refresh, auth gating.
- **Business logic** — feature-first modules under `src/features/*`
  (auth, permissions), each owning its actions/schemas/components.
- **Service layer** — Supabase clients (`src/lib/supabase`): RLS-enforced
  anon client (browser + server) and a service-role client restricted to
  workers/portal/seeding.
- **Data** — PostgreSQL via Drizzle ORM; schema in `src/db/schema` (one file
  per module), migrations in `database/migrations`.
- **Async** — `background_jobs` durable queue (foundation of the M3 file
  pipeline); jobs chain via `parent_job_id`.
- **Realtime** — all six foundation tables are in the `supabase_realtime`
  publication; RLS filters what each subscriber receives.

Approved rulings enforced: explicit PKs, `organization_id` on every
operational table, org-aware policies everywhere, tenant-as-data, dual
domains, jobs queue, realtime.

## 6. RLS policies (16) + guards

All six tables have RLS enabled. Pattern: org isolation via
`app.is_org_member(organization_id)` + action gates via
`app.has_permission(module, action)`.

- `organizations` — SELECT members; UPDATE requires `organization.update`.
- `departments` — SELECT members; INSERT/UPDATE/DELETE require
  `departments.*` permissions.
- `roles` — SELECT members; INSERT/UPDATE/DELETE require `roles.*`;
  `is_system = false` enforced in **both** USING and WITH CHECK (system
  roles can be neither modified, deleted, nor spoofed).
- `users` — SELECT members; INSERT requires `users.create`; UPDATE allows
  self **or** `users.update`, with the `trg_protect_users_privileged`
  trigger blocking self-service changes to `role_id`, `organization_id`,
  `user_id`, `status`, `employment_type`, `deleted_*` (closes the
  self-promotion-to-Owner escalation).
- `activity_logs` — SELECT members; INSERT only as oneself; **no UPDATE or
  DELETE policies** (append-only by construction).
- `background_jobs` — SELECT members only; writes are service-role only.

Helper functions (`SECURITY DEFINER`, pinned `search_path`, EXECUTE granted
only to `authenticated`): `app.current_user_organization_id()`,
`app.has_permission(module, action)`, `app.is_org_member(org_id)`.

## 7. Authentication flows

Internal users only; clients never authenticate (PRD §9).

- **Password** — server action, Zod-validated, generic failure message (no
  account-existence leak), `next`-aware redirect.
- **Magic link** — `signInWithOtp` with `shouldCreateUser: false` (no
  auto-provisioning); enumeration-safe response. Callback handles both PKCE
  (`?code=`) and cross-browser token-hash (`?token_hash=&type=email`).
- **Google OAuth** — PKCE via `signInWithOAuth`, `next` carried through the
  callback.
- **Session** — proxy refreshes on every request with `getUser()` (JWT
  revalidated, never `getSession()`); refreshed cookies are copied onto
  every redirect response (no refresh-token loss).
- **Unprovisioned identities** — authenticated users without an active
  `users` row land on public `/unprovisioned` (sign-out only), preventing
  redirect loops.
- **Defense in depth** — proxy gating is convenience; the real boundary is
  `requireCurrentUser()` at render + RLS at data level.

## 13. Security decisions

1. **RLS on from migration one** — org isolation + permission gates; not
   retrofittable later without risk.
2. **Privileged-field trigger** — RLS cannot compare OLD/NEW, so role/org/
   status changes on `users` require `users.update` permission via trigger.
3. **`is_system` in WITH CHECK** — system roles cannot be created, edited,
   deleted, or spoofed by tenants.
4. **Append-only audit** — no UPDATE/DELETE policies on `activity_logs`.
5. **`getUser()` over `getSession()`** — JWT revalidated server-side every
   request.
6. **No account enumeration** — uniform auth error/success messages.
7. **Open-redirect protection** — `next` restricted to same-site internal
   paths at every entry (proxy, actions, callback).
8. **`shouldCreateUser: false`** — magic links cannot self-provision.
9. **Service-role isolation** — documented usage contract; never imported
   client-side; portal (M4) validates share tokens before every query.
10. **SECURITY DEFINER hygiene** — pinned `search_path`, EXECUTE revoked
    from public.
11. **Soft-deleted rows remain SELECT-visible** — deliberate: restore
    capability (DBD §60) requires admins to see them; application queries
    filter `deleted_at IS NULL`. Revisit if column-level privacy demands.

## 14. Performance optimizations

- 15 targeted indexes incl. composite (`org+status`, `status+scheduled_at`,
  `org+created_at`) and partial-friendly keys for hot queries.
- Connection pooling (Supabase transaction pooler, `prepare:false`);
  pool reuse across dev hot reloads.
- `getCurrentUser` wrapped in React `cache()` — one lookup per request;
  single round trip joins user + role + org.
- Static prerendering where possible (`/`, `/portal`, `/unprovisioned`);
  dynamic only where session-bound.
- Backdrop-blur + sticky header over heavy layout effects; Turbopack build.
- Async-by-design: long work goes to `background_jobs`, not requests.
