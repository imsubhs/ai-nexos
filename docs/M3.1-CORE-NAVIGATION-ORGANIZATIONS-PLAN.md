## 1. Current-State Review (verified in code)

### 1.1 Existing organization functionality

- **Schema:** `src/db/schema/organizations.ts` — full profile surface (name, legal name, slug, logo, website, industry, timezone, currency, country, address, contact email/phone, brand colors, status, audit fields) plus `organization_sequences`. Related: `users.ts`, `roles.ts`, `departments.ts`.
- **Security:** RLS on organizations in migration `0001_security_rls_foundation.sql`; permission vocabulary already includes `organization`, `users`, `roles`, `settings` modules (`src/features/permissions/constants.ts`); `hasPermission`/`requirePermission` engine live.
- **Runtime:** `CurrentUser` (`src/features/auth/current-user.ts`) already carries `organizationName`, `organizationSlug`, `organizationLogoUrl` — consumed by the sidebar header.
- **Missing entirely:** `src/features/organizations/` does not exist — no actions, no schemas, no components, no page. Demo store (`src/lib/demo/store.ts`) has only a `DEMO_ORG_ID` constant; **no organization record and no user roster** to back a mock members/settings surface.

### 1.2 Existing dashboard functionality

- `src/app/(internal)/dashboard/page.tsx` renders four **hardcoded-zero** metric cards with stale hint copy referencing old milestone numbers ("Arrives with M2/M3"). Clients and Projects backends now exist, so two of the four metrics are wire-able today.
- Group-level `loading.tsx`, `error.tsx`, `not-found.tsx` exist for both `(internal)` and `(dashboard)` groups.

### 1.3 Existing navigation

- `AppShell` (`src/components/layout/app-shell.tsx`): server component, double auth guard (proxy + render), used by both `(internal)` and `(dashboard)` layouts.
- `AppSidebar` (`src/components/layout/app-sidebar.tsx`): static `NAV_SECTIONS` with **13 links**; collapsible icon mode; active-state highlighting; org name in header.
- `AppHeader` (`src/components/layout/app-header.tsx`): search input (non-functional placeholder), theme toggle, notifications bell (non-functional), user menu with **link to `/settings/profile` which 404s**, demo-mode badge, sign-out.

### 1.4 Missing pages (nav links with no route)

Working routes: `/dashboard`, `/projects` (+ detail + timeline), `/clients` (+ detail).
**Broken links (10 of 13):** `/tasks`, `/timeline`, `/calendar`, `/deliverables`, `/files`, `/meetings`, `/ai`, `/analytics`, `/team`, `/settings` — plus `/settings/profile` from the header menu.
In scope for 3.1: `/settings` (redirect → organization), `/settings/organization`, `/settings/profile` (minimal). Out of scope: the rest get visibly disabled ("Coming soon"), not removed — IA stays stable per SDS §16.

### 1.5 Missing CRUD

No organization actions module. Required (dispatcher/real/mock triple, matching `features/clients` pattern):

- `getOrganization` / `updateOrganization`
- `getOrganizationMembers` (users joined to roles/departments, org-scoped)
- `updateUserRole`
- `deactivateUser` / `reactivateUser`
- **Explicit deferral:** create/delete organization (single-tenant, seed-provisioned in V1).

### 1.6 Missing layouts

- No `/settings` section layout (settings sub-navigation: Organization, Profile; Members/Roles as tabs or sub-pages).
- Nav config has no notion of `enabled`/`requiredPermission` — needed to gate and disable items in one place.

### 1.7 Missing settings

- Organization profile form (all schema fields incl. brand colors, timezone, currency).
- Members management (list, role change, deactivate).
- Roles reference view (system roles read-only for MVP).
- User profile page (read-only identity + role display for MVP — header already links to it).

### 1.8 Missing permissions

- **Nav is not permission-aware** — every user sees all 13 links regardless of role.
- No `requirePermission` calls exist for organization module (no actions exist yet).
- Owner-protection rules absent: last-owner demotion, self-deactivation.
- **Defect found in review:** `DEMO_ADMIN_USER.permissions` (`src/features/auth/current-user.ts:18-36`) omits `organization`, `users`, `roles`, and `settings` modules and contains non-vocabulary keys (`ai_workspace`, `timelines`, `shares`) cast via `as unknown as PermissionMap`. As-is, every new org action and the permission-gated nav would be **denied in demo mode** (the active default). Must be reconciled with `SYSTEM_ROLES` vocabulary in this milestone.

### 1.9 Missing responsive behavior

- Sidebar/sheet mobile behavior exists via `components/ui/sidebar.tsx` + `use-mobile.ts` — no work needed there.
- Header search is `hidden md:block` (acceptable); user menu fine.
- New surfaces must be built responsive: settings sub-nav (collapse to tabs/select on mobile), org profile form (single column on mobile), members table (card list or horizontal scroll below `md`).

### 1.10 Missing loading/error states

- Route groups have boundaries; the new `/settings` tree needs its own `loading.tsx` (form/table skeletons) or must live inside an existing group to inherit them.
- Form-level states absent by definition (no forms yet): submit pending/disabled states, inline zod field errors, success/error toasts (sonner installed), optimistic-safe role-change with rollback.
- Dashboard metric cards need a Suspense skeleton if wired to live queries.

## 2. Implementation Plan (work packages, in order)

### WP1 — Navigation integrity (½ day)

1. Refactor `NAV_SECTIONS` into `src/config/navigation.ts` with per-item `{ href, title, icon, status: "live" | "coming-soon", permission?: [Module, Action] }`.
2. `AppShell` computes visibility server-side from `user.permissions` and passes filtered/flagged items to `AppSidebar`; disabled items render non-clickable with a "Soon" badge.
3. Mark live: dashboard, projects, clients, settings. Coming-soon: tasks, timeline, calendar, deliverables, files, meetings, ai, analytics, team.

### WP2 — Demo-mode permission reconciliation (½ day)

1. Rebuild `DEMO_ADMIN_USER.permissions` from `SYSTEM_ROLES` (owner: `{"*": ["*"]}` or super_admin map) — remove the unsafe cast and non-vocabulary keys.
2. Seed demo store with an organization record (matching `DEMO_ORG_ID`) and a small user roster (owner, super_admin, project_manager, team_member) to back members UI in demo mode.

### WP3 — Organizations backend (1 day)

1. `src/features/organizations/schemas.ts` — zod: org profile (URL fields, hex brand colors, IANA timezone, ISO 4217 currency, country), role-change input, deactivate input.
2. `actions.ts` (dispatcher) + `real-actions.ts` + `mock-actions.ts` for the five actions in §1.5, each guarded by `requirePermission` (`organization`/`users`/`roles` modules), org-scoped, activity-logged (real mode).
3. Guard rules in the action layer: cannot demote/deactivate the last active owner; cannot deactivate self; role changes require `roles.update` (owner/super_admin under current maps).

### WP4 — Settings section & pages (1½ days)

1. `src/app/(dashboard)/settings/layout.tsx` — settings shell with sub-nav (Organization, Profile), responsive collapse.
2. `settings/page.tsx` — redirect to `/settings/organization`.
3. `settings/organization/page.tsx` — server page fetching org + members; tabs/sections: **Profile form** (RHF + zod resolver, pending state, toast on save), **Members table** (role select, deactivate with confirm dialog), **Roles** (read-only system-roles reference).
4. `settings/profile/page.tsx` — minimal: identity card (name, email, designation, role, department), theme preference note; edit deferred.
5. `loading.tsx` for the settings tree (skeletons); rely on group `error.tsx`.
6. Permission-conditioned rendering: form read-only without `organization.update`; member controls hidden without `users.update`/`roles.update`.

### WP5 — Dashboard truth pass (½ day)

1. Wire "Active Projects" and "Clients" cards to existing `getProjects`/`getClients` counts (Suspense + skeleton).
2. Tasks/Approvals cards: keep zero but relabel hint to "Coming with Tasks module" (honest copy, no stale milestone numbers).

**Estimated total: 4 working days.**

## 6. Acceptance Criteria

1. Sidebar contains **zero dead links**: every enabled item resolves to a working route; coming-soon items are visibly disabled and non-navigable.
2. Nav items are permission-filtered (e.g., a `finance`-role user does not see Settings edit surfaces they can't use).
3. `/settings/organization` shows the real org profile (demo store or DB); edits persist and survive reload; invalid input (bad URL, bad hex color) shows inline field errors and does not submit.
4. Members table lists org users with roles; role change persists; deactivate requires confirmation and removes the member from the active list.
5. Guard rules enforced server-side: last owner cannot be demoted or deactivated; user cannot deactivate self — both return user-visible errors.
6. `/settings/profile` renders the current user's identity (header menu link no longer 404s).
7. Dashboard shows live client and project counts in demo mode; no stale milestone copy remains.
8. All new actions have dispatcher/real/mock triples; demo mode fully functional with `DEMO_MODE=true`.
9. `DEMO_ADMIN_USER.permissions` type-checks against `PermissionMap` without casts.
10. Zero TypeScript errors; build green; existing tests still pass.
