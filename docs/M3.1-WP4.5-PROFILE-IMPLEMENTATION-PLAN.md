# M3.1 · WP4.5 — User Profile (`/settings/profile`): Implementation Plan

**Status:** Proposed (awaiting approval) · **Date:** 2026-07-16 · **Author:** Principal Product Architect
**Precondition:** WP1–WP4.4 complete. No code in this document by design.

---

## 1. Repository Findings (verified against repo)

### 1.1 Current-user model
- `src/features/auth/current-user.ts` — `CurrentUser` type + `getCurrentUser()` (React `cache()`, one joined query users→roles→organizations under RLS; `DEMO_ADMIN_USER` short-circuit on `DEMO_MODE` + `demo_session` cookie) + `requireCurrentUser()` guard (redirects to `/unprovisioned`).
- `CurrentUser` carries `firstName, lastName, avatarUrl, designation, roleName, departmentId, email, organization*` — **it does not carry `phone`, `timezone`, `workingHours`, `employmentType`, or `joiningDate`**, all of which exist on the `users` table. The approved WP4 plan §2.5 lists timezone on the identity card, so the profile page cannot be rendered from `CurrentUser` alone.

### 1.2 Profile schema (DB)
- `database/migrations/0000_init_platform_foundation.sql` → `users` table: `first_name` (NOT NULL), `last_name`, `email`, `phone`, `avatar_url`, `designation`, `timezone` (default `'UTC'`), `working_hours` jsonb, `employment_type`, `joining_date`, plus audit columns (`updated_at/updated_by/version`) and soft-delete columns.
- Demo store (`src/lib/demo/store.ts`) users mirror this shape (`avatarUrl`, `designation`, `phone`, `timezone` present on roster records).

### 1.3 Auth / session utilities
- `requireCurrentUser()` + `hasPermission()` / `requirePermission()` (`src/features/permissions/engine`) — used by every settings page and every organizations action.
- Settings layout (`src/app/(dashboard)/settings/layout.tsx`) already guards `settings.read` and redirects to `/dashboard` if absent — WP4.5 inherits this for free.
- Established backend convention: **triple-file dispatcher** (`actions.ts` switching on `DEMO_MODE` between `real-actions.ts` / `mock-actions.ts`), actions **throw** (`Error` / `ZodError` / `PermissionDeniedError`), mutations call `logActivity` and `revalidatePath`.

### 1.4 Avatar support
- UI: `src/components/ui/avatar.tsx` (Base UI `AvatarPrimitive`) with `AvatarImage` + `AvatarFallback` (initials), sizes sm/default/lg; already used in `app-header.tsx` and members table.
- Upload plumbing exists but is generic: `src/lib/storage/StorageService.ts` + `SupabaseStorageProvider` (pre-signed upload URLs, bucket `nexos-assets`, mock provider in demo). **No avatar-specific upload path or public-URL handling exists**; all demo users have `avatarUrl: null` (initials fallback everywhere).

### 1.5 Preferences
- **No user-preferences column or table exists.** The only preference in the product is theme, handled client-side by `next-themes` (`ThemeProvider` in root layout; a light/dark toggle already lives in `app-header.tsx`). Persistence is localStorage — no backend.

### 1.6 Validation
- Zod, one `schemas.ts` per feature (see `src/features/organizations/schemas.ts` — includes reusable patterns: `timezoneSchema` (IANA regex), url/email/hex idioms). `src/features/auth/schemas.ts` has only login/magic-link schemas. **No profile schema exists anywhere.**

### 1.7 Reusable form components
- Proven WP4.2 stack: React Hook Form + `zodResolver` + `useTransition` + sonner toasts, composed from `field.tsx` primitives (`Field/FieldLabel/FieldContent/FieldError/FieldDescription/FieldGroup`), `Input`, `Card`, `Button` — see `settings/organization/_components/organization-form.tsx` as the template, including the `canUpdate` read-only pattern.
- `src/components/ui/` still lacks `select`, `textarea`, `alert-dialog` (WP4.3/4.4 shipped without adding them). WP4.5 profile fields are all text/tel inputs + theme buttons → **no new primitives required** (timezone as validated text input, matching the org form's timezone treatment).

### 1.8 Route/nav state
- `settings/_components/settings-nav.tsx` already lists **Profile → `/settings/profile`** and `app-header.tsx` avatar menu links there — **the route directory does not exist, so both currently 404**. This is the WP4.5 gap.
- Touch-up owed from the approved WP4 plan §2.2: `settings/page.tsx` redirects unconditionally to `/settings/organization`; it should fall back to `/settings/profile` when `organization.read` is absent.

## 2. Determinations

| Question | Answer |
| --- | --- |
| Does a Profile backend already exist? | **Partially.** Read side exists via `getCurrentUser()`, but it omits `phone`/`timezone`/`joiningDate`. No profile write path of any kind exists. |
| Does Profile require new Server Actions? | **Yes — two.** `getMyProfile()` (self, `users` row incl. phone/timezone/department name; no extra permission beyond authenticated self) and `updateMyProfile()` (self-service: firstName, lastName, phone, designation, timezone, avatarUrl). Both triple-file (real + mock + dispatcher), throwing convention, `logActivity` + `revalidatePath("/settings/profile")` on update. Widening the cached `CurrentUser` is rejected — it's a session/permission object consumed everywhere; profile detail belongs in a feature read. |
| Does Profile require schema changes? | **No.** Every editable field already exists on `users`. No preferences column is added — theme stays client-local via `next-themes` (only preference in scope). Email, role, department, employment fields are admin-managed (WP4.3 territory) and render read-only. |
| Does Profile require storage integration? | **Not in WP4.5.** Avatar is rendered (image or initials) and `avatarUrl` is accepted as a validated URL text field, mirroring the org form's `logoUrl` treatment. File-upload avatars (StorageService pre-signed flow + bucket policy + image constraints) are deferred to a dedicated backend WP — same deferral pattern WP4.3 used for `last_active`. |

**Scope note:** the approved WP4 plan §2.5 scoped the profile page read-only. WP4.5 being carved out as its own work package, this plan proposes the minimal self-service edit (name, phone, designation, timezone, avatar URL) because the backend cost is one action pair and it removes the "read-only note" debt. If leadership prefers strict M3.1 scope, drop `updateMyProfile()` and render everything read-only — every other section of this plan stands unchanged.

## 5. Acceptance Criteria

1. `/settings/profile` no longer 404s from either the settings sub-nav or the header avatar menu.
2. Identity card renders the current user's avatar (initials fallback when `avatarUrl` null), full name, email, role name, designation, department, and timezone — from live data (demo store in demo mode).
3. Editable fields (first name, last name, phone, designation, timezone, avatar URL) save via `updateMyProfile`, persist across reload, and show a success toast; header avatar/name reflect the change after revalidation.
4. Invalid input (empty first name, malformed timezone, malformed avatar URL) shows inline field errors and does not submit; server-side Zod rejection surfaces gracefully; `PermissionDeniedError`/business errors toast verbatim per the established mapping.
5. Email, role, and department render read-only with a muted "managed by your administrator" note — no edit affordance.
6. Theme selector (light/dark/system) works, persists across reload (next-themes), and stays in sync with the header toggle.
7. `updateMyProfile` can only mutate the caller's own row (enforced server-side, not just UI) and writes an activity-log entry.
8. Page renders skeletons via `loading.tsx`; submit shows pending state (disabled + label).
9. Usable at 375px (single-column cards, no horizontal scroll); dark-mode pass clean.
10. Keyboard/screen-reader pass: all inputs labelled via `field.tsx`, errors associated, theme selector operable by keyboard, headings hierarchical (`h2` per card under the layout's `h1`).
